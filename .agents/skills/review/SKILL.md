# Code Review

## 리뷰 대상

| 모드 | 사용 시점 | diff |
|------|-----------|------|
| `staged` | `commit` 스킬 검증 후, 커밋 직전 | `git diff --staged` |
| `branch` | `pr` 스킬에서 PR 생성 직후 | `git fetch origin && git diff origin/<base>...HEAD` |
| `ci` | `ai-review` 워크플로 | 워크플로가 제공한 diff 파일 |

- diff만 보지 말고, 변경된 함수의 호출부·관련 DTO·테스트 파일을 열어 맥락을 확인한다
- `pnpm-lock.yaml`, `dist/`, `coverage/`, 생성 파일(`node_modules/.prisma`)은 리뷰하지 않는다
- 리뷰는 **보고만** 한다. 코드 수정은 사용자가 요청할 때만 (`ci` 모드에서는 절대 수정하지 않음)

## 관점 (우선순위 순)

1. **보안**
   - 비밀값(API 키, 비밀번호, 토큰, DB URL) 하드코딩, `.env*`/`cert/` 커밋
   - admin 엔드포인트에 `JwtAuthGuard` 누락, public API에서 비공개 데이터(`isShow: false` 등) 노출
   - 에러 응답에 Prisma 원문/스택/연결 정보 노출, `$queryRawUnsafe`에 사용자 입력 연결
2. **정확성**
   - 여러 쓰기/관계 테이블 갱신이 `$transaction` 밖에서 수행되거나 실패가 무시됨 (`catch` 후 삼킴)
   - 없는 리소스에 500 대신 `NotFoundException`(404), 잘못된 입력은 `BadRequestException`(400)
   - 페이징 `page`/`size` 숫자 변환·기본값·`skip` 계산, 검색 조건과 count 조건 불일치
   - `null`/`undefined`, 빈 배열, 경계값 처리
3. **테스트** (`tdd` 원칙)
   - 수정된 `src/**/<name>.ts`에 대응하는 `<name>.spec.ts` 추가/수정이 있는지
   - 동작 변경·버그 수정에 그 동작을 검증하는 케이스가 있는지, 실제 DB 연결 테스트가 아닌지
   - 테스트가 환경(`.env`, 시간, 순서)에 의존하지 않는지 (CI에는 `.env`가 없다)
4. **API 호환성**
   - 응답 필드 삭제/이름 변경, 상태 코드 변경 → 프론트엔드 영향 여부를 명시
   - Prisma 스키마 변경 시 마이그레이션 포함 여부, `schema.prisma` generator 설정 변경의 배포 영향
5. **컨벤션** (`AGENTS.md`)
   - DTO 이름 `<Scope><Domain><Action>Request|Response`, `class-validator`/Swagger 데코레이터, `dto/index.ts` re-export
   - `src/...` 절대경로 import, 새 모듈의 `index.module.ts` 등록
   - 새 환경변수의 README 문서화, `console.log` 디버그 코드·미사용 import
6. **성능**: 루프 안 쿼리(N+1), 불필요한 전체 조회, 인덱스 없는 검색 조건

## 심각도 기준

- 🔴 **반드시 수정**: 보안 문제, 데이터 손상/유실 가능성, 명백한 버그, 배포 시 장애 가능성, 테스트 없는 동작 변경
- 🟡 **권장**: 엣지 케이스 누락, 에러 처리 미흡, 컨벤션 위반, 유지보수 저하
- 🟢 **참고**: 취향 차이, 근거가 확실하지 않은 추측성 지적

근거(코드 위치와 이유)를 제시할 수 없는 지적은 🔴/🟡로 올리지 않는다. 지적할 것이 없으면 억지로 만들지 않고 "발견 사항 없음"으로 쓴다.

## 출력 형식

```markdown
## 코드 리뷰: <🔴 수정 필요 | 🟡 권장 사항 있음 | ✅ 문제 없음>

<변경 요약 1~2문장>

### 발견 사항
- 🔴 `src/path/file.ts:42` — <문제>. <근거>. 제안: <수정 방향>
- 🟡 `src/path/file.ts:10` — <내용>
- 🟢 <내용>

### 테스트
<변경 파일 대비 테스트 추가/수정 여부, 누락된 케이스>

### 확인한 범위
<리뷰한 파일 수, 제외한 파일, 맥락 확인을 위해 열어본 파일>
```

## 자동 실행 시나리오

| 시점 | 실행 주체 | 모드 | 결과 | 다음 동작 |
|------|-----------|------|------|-----------|
| 에이전트가 커밋 (`commit` 스킬 5단계) | 로컬 에이전트 | `staged` | 사용자에게 보고 | 🔴 없음 → 커밋 / 🔴 있음 → 중단, 사용자 판단 |
| 에이전트가 PR 생성 (`pr` 스킬 10단계) | 로컬 에이전트 | `branch` | `ai-review:local` 댓글 | PR URL과 리뷰 요약 보고 |
| PR 생성·푸시·reopen·ready for review | GitHub Actions | `ci` | `ai-review:ci` 댓글 생성/갱신 | 체크는 항상 통과 (댓글만) |
| PR 댓글 `/review` (소유자·협업자) | GitHub Actions | `ci` | `ai-review:ci` 댓글 갱신 | 문서만 바뀐 PR도 리뷰 |
| 에이전트가 머지 (`pr` 스킬 머지 절차) | 로컬 에이전트 | - | 최신 리뷰 댓글 확인 | 🔴 없음 + 체크 통과 → 머지 |
| 사용자가 "리뷰 해줘" | 로컬 에이전트 | 상태에 맞게 | 보고 (PR이 있으면 댓글도) | - |

- **🔴 처리 루프**: 🔴 보고 → 사용자가 "고쳐" → `tdd`로 수정 → 재스테이징 → 다시 `staged` 리뷰 → 커밋. 푸시하면 CI 리뷰가 같은 댓글을 갱신한다
- **오탐**: 근거가 틀렸다고 판단되면 사용자에게 근거와 함께 보고하고, 사용자가 진행을 명시하면 커밋/머지한 뒤 그 결정을 보고에 남긴다
- **사용자가 직접 PR을 올린 경우**: 로컬 리뷰는 돌지 않고 CI 리뷰만 실행된다. GitHub UI 머지는 막을 수 없으므로 리뷰 댓글은 사용자가 확인한다
- **CI 리뷰가 생략되는 경우**: `CURSOR_API_KEY` 없음, 에이전트 실행 실패, draft PR, 포크 PR, `.md`만 바뀐 PR(`/review`로 수동 실행 가능). 200KB 초과 diff는 앞부분만 리뷰하고 그 사실을 표시한다
- **긴급 hotfix**: 리뷰는 동일하게 실행한다. 사용자가 🔴를 알고 머지를 지시하면 머지하고, 남은 🔴는 후속 작업으로 보고한다

## 결과 처리

- `staged`: 🔴가 있으면 커밋하지 않고 사용자에게 보고한다. 사용자가 알고도 진행을 요청한 경우만 커밋하고 보고에 남긴다
- `branch`: 결과를 PR 댓글로 남긴다 (`gh pr comment <번호> --body-file <파일>`). 본문 첫 줄에 `<!-- ai-review:local -->`를 넣는다
- `ci`: 출력 형식의 마크다운만 출력한다 (댓글 작성은 워크플로가 담당)
- 머지 전 확인: `pr` 스킬의 머지 절차에서 🔴 항목이 해결됐는지 확인한다
